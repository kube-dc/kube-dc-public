## HAMi-core compute qualification

`run-hami-core-throttle.sh` used HAMi v2.9.0's published PyTorch matrix
multiplication workload, pinned
`docker.io/pytorch/pytorch@sha256:68c022c2f4627943a6f3e574cfd2c8ae4256210d5f66ae2b117942e0a8d4fa9d`,
and requested 4096 MiB plus 30% compute with
`GPU_CORE_UTILIZATION_POLICY=force`.

The runtime wiring was verified directly: `CUDA_DEVICE_SM_LIMIT=30`, the unique
HAMi shared-cache path, `/etc/ld.so.preload`, mapped `libvgpu.so`, the
4096-MiB virtual memory view, the exact allocation annotation, and HAMi's own
per-container monitor metric all matched the test Pod.

Results:

- the published workload with only a 30-second warm-up averaged 52.64% across
  36 five-second UUID-specific samples; its first eight samples were 100%, then
  the watcher began converging;
- the same workload after a 120-second warm-up averaged 34.31% across 36
  five-second samples, passing the retained 15–45% steady-state band;
- a pure-cuBLAS batched matrix-multiply loop averaged 58.11% across 36
  five-second samples, 69.16% across 180 one-second samples, and 66.97% after a
  90-second warm-up in a short diagnostic window.

Every run started with zero active holders under the atomic lock and restored
zero fixtures, no lock, the unsuspended canary, `pod-hami` mode, and 20 shares.
The evidence proves steady-state enforcement for HAMi's documented workload,
but also proves that a 30% request is not a hard instantaneous or universal CUDA
execution cap on this stack. B-004/D-003 therefore remain open; the billing
dimension is an aggregate entitlement and cooperative software target, not a
hard compute partition.

## Frozen-plugin detection and recovery

`run-hami-plugin-outage.sh` passed against the idle pool. Its cgroup-guarded
`STOP` froze the one real `nvidia-device-plugin` process while the node kept
advertising 20 cached shares. A manual Job created from the allocation canary
remained active, and the script observed
`KubeDcHamiAllocationCanaryStuck{alertstate="firing"}` through Prometheus's
Kubernetes service proxy.

After guarded `CONT`, the blocked canary completed, a fresh recovery canary also
completed, the alert cleared, and allocatable capacity remained 20. The trap
removed both manual Jobs, restored the CronJob to unsuspended, and released its
lock. The final audit found the DaemonSet 1/1 Ready, no firing stuck alert, and
the scheduled canary successful again.

## KubeVirt V100 passthrough and rollback

The fleet entered the reversible `vm-passthrough` overlay under the shared
hardware lock. GPU Operator 26.3.3 converged its VFIO manager, sandbox device
plugin, and sandbox validator without a node reboot or drain. Both physical
functions, `0000:81:00.0` and `0000:c1:00.0`, bound to `vfio-pci`; the sandbox
plugin advertised exactly two
`nvidia.com/GV100GL_TESLA_V100_PCIE_32GB` devices. KubeVirt 1.8.1 allowlisted
that exact case-sensitive resource for `10DE:1DB6` with
`externalResourceProvider: true` and no deprecated GPU feature gate.

The first live VM exposed a previously dry-run-invisible admission interaction:
the HAMi Pod policy rejected KubeVirt's profile-labelled launcher Pod. The
catalog-derived fix admits the native VM resource only when the selected VM
profile matches, a controller `VirtualMachineInstance` owner is present, and
the CREATE caller is the configured KubeVirt controller identity. A seven-case
live matrix proved the controller path while denying tenant direct-resource and
spoofed-owner requests; the original 37 HAMi Pod cases and 44 VM/VMI cases also
passed with zero CEL warnings.

`run-vfio-vm-lifecycle.sh` then reported:

```text
PASS preflight: mode=vm-passthrough resource=nvidia.com/GV100GL_TESLA_V100_PCIE_32GB allocatable=2 activeHolders=0
PASS attach: VMI Ready with VFIO hostdev and non-migratable condition
PASS lifecycle: stop released device; start created Ready VMI with a new UID
PASS exclusivity: two VMs consumed two devices; third request queued
PASS migration: live migration denied with HostDeviceNotLiveMigratable
PASS queue: released device assigned to the waiting third VM
PASS cleanup: namespace=gpu-vfio-suite-007 will be removed
```

Each Ready launcher requested one exact native resource, had a controller VMI
owner, and its libvirt XML contained a `vfio` PCI hostdev with the catalogued
`ua-gpu-gpu0` alias. The first VMI completed create, Ready, stop, device release,
and start with a different UID. Two concurrent VMIs consumed the two physical
devices; a third launcher remained unscheduled with `Insufficient
nvidia.com/GV100GL_TESLA_V100_PCIE_32GB`, then became Ready after the first VM
stopped. `virtctl migrate` was rejected by KubeVirt with
`HostDeviceNotLiveMigratable`. The two unrelated VMIs already running on
`host5-a` stayed Running and Ready throughout the driver handoffs.

Fleet commit `92bf802` restored the final `pod-hami` service mode. Without a
reboot, both BDF driver links returned to `nvidia`, the sandbox resource fell to
zero, the NVIDIA driver and HAMi DaemonSets became Ready, and
`nvidia.com/gpu` returned to 20. A manual allocation canary completed. The one
scheduled canary created during HAMi's expected five-minute node lock failed and
temporarily fired the stale/stuck alerts; the next ordinary CronJob completed
and all six GPU/HAMi alerts became inactive. No hardware lock, VM test namespace,
or active passthrough holder remained. This closes the bind, use, exclusivity,
release, migration-denial, unbind, and service-recovery proof; guest NVIDIA
driver/CUDA qualification remains separate.
